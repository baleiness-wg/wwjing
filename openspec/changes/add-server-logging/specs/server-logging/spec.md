# Spec Delta

## Purpose

为 Node 服务建立统一、结构化且可长期查询的日志能力，使开发人员能够定位请求、错误和运行状态，并使单机或容器部署能够依赖运行环境保存历史日志，而不把日志管理逻辑分散在业务代码中。

## ADDED Requirements

### Requirement: 服务输出统一的结构化应用日志

系统 MUST 为服务启动、数据库迁移、关键业务操作和运行异常提供统一的日志级别与结构化字段；生产环境日志 MUST 输出到标准输出或标准错误，以便部署环境采集。

#### Scenario: 服务启动时记录运行信息

- **WHEN** Node 服务成功启动
- **THEN** 系统输出一条 info 级别日志，至少包含服务名称、运行环境、监听地址和端口

#### Scenario: 数据库迁移完成时记录结果

- **WHEN** 数据库迁移成功执行或跳过已执行的迁移
- **THEN** 系统输出可识别迁移文件名和执行结果的日志

#### Scenario: 生产日志可被机器解析

- **WHEN** 服务在生产环境运行
- **THEN** 每条日志均以结构化记录输出，并包含时间、级别、服务标识和消息字段

### Requirement: 系统记录 HTTP 请求及请求关联信息

系统 MUST 记录进入服务的 HTTP 请求及其完成结果，并 MUST 为请求提供可贯穿请求处理过程的关联标识。

#### Scenario: 请求成功完成

- **WHEN** 客户端请求接口并获得成功响应
- **THEN** 系统记录 HTTP 方法、请求路径、响应状态码、处理耗时和请求关联标识

#### Scenario: 请求返回错误

- **WHEN** 接口返回客户端错误或服务端错误
- **THEN** 系统记录对应请求的状态码、处理耗时、请求关联标识和错误级别

#### Scenario: 业务日志关联 HTTP 请求

- **WHEN** 请求处理过程输出业务日志
- **THEN** 业务日志可以通过请求关联标识与该请求的访问日志对应

### Requirement: 系统记录可诊断的错误信息

系统 MUST 在未处理异常和统一错误处理中记录错误类型、错误消息和堆栈信息，并 MUST 保留客户端所需的稳定错误响应行为。

#### Scenario: 统一错误处理中记录异常

- **WHEN** 请求处理链收到未预期异常
- **THEN** 系统记录错误对象及请求上下文，并向客户端返回统一的服务端错误响应

#### Scenario: 已知业务错误使用适当级别

- **WHEN** 请求因未认证、参数错误或文件大小超限被拒绝
- **THEN** 系统记录可用于诊断的警告或错误日志，但不将正常客户端错误误记为未处理服务崩溃

### Requirement: 日志不得泄露敏感数据

系统 MUST 在输出日志前排除或脱敏认证凭证、密码、Authorization 请求头、完整用户文字内容、文件二进制和数据库凭据。

#### Scenario: 登录请求被记录

- **WHEN** 用户提交登录请求并产生访问日志或错误日志
- **THEN** 日志不包含密码、完整 Authorization 值或 JWT 内容

#### Scenario: 文件接口被记录

- **WHEN** 用户上传或下载文件并产生日志
- **THEN** 日志可以记录文件类型、文件大小和结果，但不记录文件二进制内容

### Requirement: 历史日志可以按部署环境查询

系统 MUST 以标准输出和标准错误提供日志，使单机部署可以通过 systemd/journald 或进程管理器保存并按时间查询历史日志，使容器部署可以通过容器日志机制采集；应用日志组件不要求直接连接 Elasticsearch。

#### Scenario: 单机服务查询历史日志

- **WHEN** 服务已运行数日且部署环境配置了日志保留策略
- **THEN** 运维人员可以按服务和时间范围查询数日前的日志

#### Scenario: 容器服务查询历史日志

- **WHEN** 服务运行在容器中且容器日志保留策略仍覆盖目标时间范围
- **THEN** 运维人员可以按容器和时间范围查询历史标准输出日志

#### Scenario: 日志超过保留周期

- **WHEN** 目标日志早于部署环境配置的保留周期
- **THEN** 系统允许该日志被清理，并通过日志保留配置明确可查询的时间范围
