# Spec Delta

## Purpose

为 Node 服务提供统一的结构化日志能力，使开发人员能够查看服务启动、HTTP 请求和运行错误，并在单机或集中式部署环境中按时间、请求 ID 和业务字段检索历史日志，同时避免输出认证凭据和用户内容等敏感数据。

## ADDED Requirements

### Requirement: 服务必须输出结构化应用日志

系统 MUST 使用统一日志接口输出服务启动、数据库迁移和应用运行状态日志；生产环境日志 MUST 输出结构化 JSON，并至少包含时间、日志级别、服务名称、运行环境和消息字段。

#### Scenario: 服务启动日志可检索

- **WHEN** Node 服务成功启动
- **THEN** 系统输出一条包含服务名称、监听地址、运行环境和启动消息的结构化日志

#### Scenario: 日志级别过滤生效

- **WHEN** 服务配置了日志级别
- **THEN** 系统不输出低于配置级别的日志，并输出达到或高于配置级别的日志

### Requirement: 系统必须记录 HTTP 请求结果

系统 MUST 为进入 Express 服务的 HTTP 请求记录请求方法、请求路径、响应状态码和响应耗时，并 MUST 为同一请求提供可关联的请求 ID。

#### Scenario: 成功请求产生访问日志

- **WHEN** 客户端请求健康检查或业务接口并获得成功响应
- **THEN** 系统输出包含请求方法、路径、状态码、耗时和请求 ID 的访问日志

#### Scenario: 错误响应产生访问日志

- **WHEN** 请求因认证失败、参数错误或服务器异常返回错误状态码
- **THEN** 系统仍输出对应的访问日志，并保留实际响应状态码和请求 ID

### Requirement: 系统必须记录可诊断的错误信息

系统 MUST 在请求错误和未处理应用错误发生时记录错误级别日志；日志 MUST 包含错误类型、消息和堆栈信息，并 SHOULD 包含关联请求 ID，但不得因此改变既有错误响应状态码和响应结构。

#### Scenario: 中间件错误包含堆栈

- **WHEN** Express 错误处理中间件收到异常
- **THEN** 系统输出错误类型、错误消息和堆栈，并按既有规则返回客户端错误响应

#### Scenario: 数据库迁移失败可定位

- **WHEN** 数据库迁移失败
- **THEN** 系统输出迁移失败消息和错误诊断信息，并以失败状态结束迁移进程

### Requirement: 日志不得泄露敏感数据

系统 MUST 禁止在日志中记录密码、JWT、Authorization 请求头、文件二进制内容和用户保存的文字正文；文件操作日志最多记录文件名、媒体类型和文件大小等必要元数据。

#### Scenario: 登录请求不记录密码和令牌

- **WHEN** 用户执行登录或认证相关请求
- **THEN** 产生的日志不包含密码、完整 Authorization 请求头或 JWT 内容

#### Scenario: 内容传输日志不记录内容正文

- **WHEN** 用户保存或读取文字、文件内容
- **THEN** 产生的日志不包含文字正文和文件二进制，仅可记录必要的类型、大小和结果信息

### Requirement: 日志输出必须适配开发和生产环境

系统 MUST 在开发环境提供可读的终端日志，在生产环境输出可被日志采集器处理的 JSON 标准输出；系统 MUST 不要求业务代码直接绑定 Elasticsearch、Kibana 或其他具体日志平台。

#### Scenario: 开发环境查看日志

- **WHEN** 服务以开发环境启动
- **THEN** 开发人员可以在终端看到可读的服务和请求日志

#### Scenario: 生产环境交给运行平台保存

- **WHEN** 服务以生产环境启动并由 PM2、Docker 或 systemd 管理
- **THEN** 服务将 JSON 日志写入标准输出，运行平台可以保存、轮转或转发历史日志
